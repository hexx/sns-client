# Q12: 投稿一覧の API 形状

Q11 は A（同一オーバーレイ内で置換）で確定。最後に**投稿一覧の取得 API の形**を決めたい。概要（Profile）と一覧（ページング付き）を同じ応答に載せるか、分けるかの話です。

前提となる事実（コードベース確認済み）:
- タイムラインは `GET /api/timeline` が `{posts, nextCursor}` を返し、クライアントは cursor で追加読み込みする既存パターンがある（`TimelineResponse`）。スレッドも `nextCursor`（Misskey のみ）を持つ。
- プロフィール概要は1回の取得で済むが、投稿一覧は無限スクロールで何度も取得する。**概要と一覧は更新頻度が違う**（一覧だけ再取得・追加読み込みしたい）。
- nostr はブラウザ直接で、概要（kind:0）と一覧（kind:1）を別々に組み立てるのが自然（`queryRelays` は kinds 指定で使い分け可能）。

## A: 概要と一覧を別ルートにする（推奨）
- `GET /api/profile?provider=&id=` → Profile（概要のみ）
- `GET /api/profile/posts?provider=&id=&cursor=` → `TimelineResponse` と同じ `{posts, nextCursor}` 形状
- nostr はブラウザ直接で同じ2系統を組み立てる（shared/nostr.ts に関数追加）

- 推奨理由: 無限スクロールの追加読み込みで概要を再取得しないで済む。応答形状が既存 `TimelineResponse` と同一なので、クライアントの追加読み込み処理（Timeline の実装）をそのまま流用できる。エラーも分離できる（概要が取れなくても一覧は見える等）。
- デメリット: ルートが1本増える（ただし形状は既存の再利用で、新概念は無い）。

## B: 1つのルートにまとめる
`GET /api/profile` が概要＋初回の投稿一覧をまとめて返し、追加読み込みは別 cursor ルート（または同じルートに cursor を付ける）で行う。

- 推奨理由（こちらの立場）: ルートが1本で済む。
- デメリット: 初回応答に「概要＋一覧」の2系統が同居し、追加読み込み時の応答は一覧だけ、と形状が場合分けになる（一貫性が落ちる）。既存 TimelineResponse の再利用もしにくい。
