# 表示するタイムラインを「1つ以上の Source の集合（View）」として定義し、クライアント側で時系列合成する

複数 SNS を1本にまとめて見たい、という要求に対し、表示単位を **View = 1つ以上の Source の集合** と定義する。Source は「1つの Provider に属する1つの投稿ストリーム」（home / Bluesky feed / Misskey antenna など）。クライアントが Source ごとに fetch・カーソル管理し、`createdAt` 順に合成して1本の Timeline を描画する。統合ホームは `[bluesky/home, misskey/home]` の2ソース View、単体フィード/アンテナは1ソース View（合成の退化ケース）として、同じ機構で扱う。

View の定義（どの Source の組み合わせか）は **BFF が `GET /api/views` で配信する単一のソースオブトゥトゥース**に置き、クライアントは起動時に取得してタブを描画する。これにより、PWA の stale キャッシュに左右されず、スマホでも PC でも同じ View が見える。

合成をサーバではなくクライアントに置いたのは、(1) カーソル方式が Provider ごとに異なる（Bluesky=cursor 文字列、Misskey=`untilId`）ため複合カーソルをサーバで管理すると状態が複雑化する、(2) 片方の Provider が落ちても他方を表示できる部分障害耐性、(3) 「N ソースを合成する」1つのロジックで将来のフィード/アンテナ混在 View にもそのまま拡張できる、ため。

## Considered Options

- プロバイダ切替（タブごとに1 Provider の TL を1本ずつ表示）— 却下：要求は「1本にまとめて見たい」なので満たさない
- サーバ側で合成（BFF が両 Provider をマージして返す）— 却下：複合カーソル管理が複雑・部分障害に弱い・View が増えるほどサーバが太る
- **View = N Sources をクライアントで合成、定義は BFF 配信（採用）**

## Consequences

- 「最古の表示投稿が新しい側の Source を次にページングする」という合成ページングロジックがクライアントに必要。
- クライアントの Timeline 状態が「1本」から「Source ごとのカーソル＋合成結果」に太くなる（既存の「薄い fetch クライアント」方針からの意図的な逸脱）。
- View 定義を BFF 配信にしたため、将来 View を利用者編集可能（カスタム View）にしても、形は不変・置き場所が KV 等に変わるだけで済む。固定プリセットの当面は Worker 側コードで定義する。
- 複数 Provider が混在する View では投稿先が曖昧になるため、投稿ボックスに明示的なターゲット Provider 選択を設ける（当面は単一ターゲット、クロスポストは将来拡張）。
