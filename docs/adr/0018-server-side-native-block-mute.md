# ブロック・ミュートはサーバー側（Provider ネイティブ）方式とし、クライアント側フィルタは採用しない

ユーザーのブロック・ミュート（[block-mute-spec.md](../block-mute-spec.md)）は、各 SNS のネイティブ API を BFF が dispatch して **Provider 本体の状態として成立させる**。アプリ内に非表示リストを永続化して描画時に隠すクライアント側フィルタは採用しない。理由: ブロックは安全機能であり、通知・メンション等アプリ外でも効いてこそ意味があること、本アプリは単一アカウント構成（認証情報は Worker の env）でサーバー側の状態が唯一の真実であること、既存の action dispatch パターン（like / repost / reaction）にそのまま乗ること。

## Considered Options

- **クライアント側フィルタ** — 実装は軽く Provider 差異も吸収できるが、通知・リプライは抑止されず、本家アプリとの状態齟齬が生まれる。キーワードミュートや Nostr の非表示など、将来のクライアント側フィルタ群とは別系統として残す。
- **ハイブリッド（ブロック=サーバー側、ミュート=クライアント側）** — ミュートをアプリ固有の状態にできるが、単一アカウント構成ではサーバー側に寄せる方が状態が一貫し、UI も一本化できる。

## Consequences

- `Author` に必須の `id`（opaque な Provider 固有識別子: bsky=DID / misskey=userId / nostr=pubkey）を追加する。`handle` は可変の表示名であり操作対象にしない。
- **Nostr（読み取り専用 Provider）は本機能の対象外**。Nostr の非表示は将来、クライアント側フィルタとしてキーワードミュートと同一の土俵で設計する。
- 自分自身への操作を UI で隠すため、BFF に自分の actor id を公開する `GET /api/me` を新設する。
- 画面上の即時除去（タイムラインの除去・スレッドのプレースホルダ化）にはセッション内の一時フィルタを使うが、これは描画上の反映であり本方式の主体ではない（永続化しない）。
