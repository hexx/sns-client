# ユーザーのブロック・ミュート仕様

> 複数 SNS を1画面で扱う PWA クライアント（[sns-client-spec.md](./sns-client-spec.md)）に、
> **ユーザー単位のブロック・ミュート**を追加する拡張の確定仕様。デッキ UI・スマホ UI の両方に適用する。
> 作成: grill-with-docs セッション（全10問合意）に基づく。
> 関連仕様: [ADR-0018](./adr/0018-server-side-native-block-mute.md)（方式の決定）。用語は [CONTEXT.md](../CONTEXT.md)（`Author` / `block` / `mute`）参照。

---

## 1. 背景・目的

- タイムラインに「**見たくない**ユーザー」と「**関わりを断ちたい**」ユーザーが現れる。前者はノイズ低減、後者は安全上のニーズで、動機が異なる。
- 現在の PostCard の操作は投稿自体に対するもの（reply / repost / like / reaction）のみで、**ユーザー単位の操作が一切存在しない**。
- 本仕様はブロック・ミュートを **各 SNS 本体（Provider 側）の状態として成立**させ、アプリ内外で一貫した効果を得る。

## 2. スコープ

### 今回（確定）

- **方式**: サーバー側（Provider ネイティブ）。BFF が各 SNS のブロック/ミュート API を dispatch する。クライアント側フィルタは「画面上の即時除去」のためのセッション内一時フィルタのみで、永続化しない。
- **対象 Provider**: Bluesky + Misskey の2つ。
- **アクション**: ブロックとミュートの2つ。Misskey のミュート期限は**無期限のみ**（期限 UI は持たない）。
- **操作入口**: PostCard の投稿者行のオーバーフローメニュー（⋯）。ThreadView の各ノードにも同じメニューを再利用。
- **確認 UI**: ブロック＝確認ダイアログ、ミュート＝即実行＋トースト。
- **即時反映**: 成功したら画面上から即時除去（タイムラインは除去、スレッドはプレースホルダ化）。
- **解除**: トーストの一時的な「取り消し」のみ。

### 非目標（今回は対象外）

- **Nostr**: 読み取り専用 Provider でサーバー側ブロック/ミュートが存在しないため対象外（クライアント側フィルタは別機能として将来設計。§8）。
- **管理一覧画面**: ミュート・ブロック中の一覧と解除 UI（§8）。
- **再共有者（`repostedBy`）への操作**: 対象は投稿者（`Post.author`）のみ（§8）。
- **プロフィール画面**: ユーザー詳細 View は作らない。
- **キーワードミュート**: クライアント側フィルタの土俵が同じだけで別機能（[deck-view-spec.md](./deck-view-spec.md) の将来候補のまま）。

## 3. ドメイン・モデル

### 3.1 `Author.id`（必須の追加）

- `Author` に **必須の `id: string`** を追加する。Provider 内で安定した opaque なアクター識別子。
  - Bluesky: DID（`app.bsky.graph.block` の `subject.did`、`muteActor` の対象）
  - Misskey: ユーザー ID（`blocking/create` / `mute/create` の `userId`）
  - Nostr: pubkey（マッパーが設定可能。将来のクライアント側フィルタに備える）
- `handle` は変わりうる表示名であり、操作の対象にしない（BFF はマッピング時に DID / userId を保持しているため取得コストは小さい）。
- 既存の `Post.id`（Provider 固有の opaque ID）と同じ命名・思想。

### 3.2 block / mute の意味論

| | mute（ミュート） | block（ブロック） |
|---|---|---|
| 性格 | 柔らかい・気軽。ノイズ低減 | 硬い・安全機能 |
| Bluesky | `muteActor`（TL から見えなくなる。相手に通知なし、いつでも解除可） | `block` レコード（相互作用を遮断。投稿も見えなくなる） |
| Misskey | `mute/create`（TL・通知から隠れる。相手に通知なし） | `blocking/create`（相互作用を遮断） |
| UI 上の扱い | 即実行＋トースト | 確認ダイアログ後、実行 |

- 両操作とも**自分のアカウントには適用できない**（Provider 側でエラー。UI で防止する、§5.1）。
- リモートユーザー（Threads 等の連合経由）も Misskey 側のブロック/ミュートで自然にカバーされる。

## 4. API

既存の action dispatch パターン（`/api/likes` / `/api/reposts`）に合わせる。`shared/constants.ts` の `API` に `mutes` / `blocks` / `me` を追加する。

### 4.1 エンドポイント

| エンドポイント | メソッド | ボディ | 成功レスポンス |
|---|---|---|---|
| `/api/mutes` | POST | `{ provider, actorId }` | `{}` |
| `/api/mutes` | DELETE | `{ provider, actorId }` | `{}` |
| `/api/blocks` | POST | `{ provider, actorId }` | `{}` |
| `/api/blocks` | DELETE | `{ provider, actorId }` | `{}` |

- `provider` は `isWritableProvider`（bluesky / misskey）に限る。`actorId` は `Author.id` をそのまま渡す（opaque）。
- Provider への実装:
  - Bluesky: `muteActor` / `unmuteActor`（handle ではなく DID で解決）、`app.bsky.graph.block` レコードの作成/削除（`getProfile` で既存 block レコードを確認してトグル）。
  - Misskey: `mute/create` / `mute/delete`、`blocking/create` / `blocking/delete`。
- **エラー時**: Provider が失敗したら 4xx を返す。クライアントは**状態を変えず**エラートーストを出すだけ。

### 4.2 自分の actor id の公開（`GET /api/me`・新設）

- 自分の投稿への操作項目の非表示判定（§5.1）に使う。
- レスポンス: `{ me: { bluesky: { actorId: string } | null, misskey: { actorId: string } | null } }`（env に認証情報がある Provider のみ値を持つ）。
- 取得方法は実装依存: Bluesky は handle → DID 解決、Misskey は `/api/i`。

## 5. UI

### 5.1 操作入口（オーバーフローメニュー）

- **PostCard の投稿者行に ⋯ メニューを新設**。項目:
  - 「このユーザーをミュート」
  - 「このユーザーをブロック」
- **ThreadView の各ノード**（祖先・子孫・フォーカス投稿）にも同じメニューを再利用する。
- **自分の投稿では両項目を非表示**（判定: `author.id === me[provider].actorId`）。メニュー自体は残す（将来の「リンクをコピー」等の置き場）。
- **quote card は表示専用**（CONTEXT.md 既定）のためメニューなし。
- 対象は常に**投稿者（`Post.author`）**。`repostedBy` への操作は持たない（§8）。

### 5.2 確認 UI

- **ブロック**: 確認ダイアログ。対象のハンドルを表示し、影響を1行説明する（例: 「このユーザーの投稿が見えなくなり、相手からはあなたへのリプライ等ができなくなります」）。「ブロック」で確定、「キャンセル」で中止。
- **ミュート**: 確認なしで即実行。

### 5.3 トーストと一時的な取り消し

- 成功トースト: 「@handle をミュートしました」「@handle をブロックしました」。
- トーストに**「取り消す」**ボタンを表示（約10秒）。押すと対応する DELETE を呼び、解除する。
- 取り消し後は**除去した投稿の再挿入はしない**（次回の取得で自然に戻る）。
- ブロックの取り消しも同じトーストの「取り消す」で行う（確認ダイアログは最初の実行時のみ）。
- トーストの時間経過後・リロード後の解除手段は**本家アプリに委ねる**（管理一覧は §8 の将来拡張）。

### 5.4 即時反映（成功時）

- **タイムライン**: 表示中の全投稿から、該当 `author.id` の投稿を**即時除去**する（リポストとして表示されているものも含む。セッション内の一時フィルタとして描画時に適用）。
- **スレッド**: 該当ノードを**「この投稿は取得できません」プレースホルダ**（`ThreadNode.unavailable` / `quoteUnavailable` と同じイディオム）に置換する。木構造の連続性は保たれる。フォーカス投稿自身の著者をブロック/ミュートした場合も同様。
- サーバー側では既にブロック/ミュートが成立しているため、以降の取得では Provider が対象ユーザーの投稿を返さない（TL の種別による挙動差は実装時に検証）。

## 6. エッジケース

1. **自分の投稿**: ミュート/ブロック項目を非表示（§5.1）。
2. **リポスト表示**: 対象は `author` のみ。ミュートした投稿者の投稿は、リポストされた形で表示されている場合も除去される。
3. **Provider エラー**: エラートーストのみ。画面・状態は不変。
4. **操作直後の誤操作**: トーストの「取り消し」（約10秒）で解除。取り消し後は再挿入せず、次回取得で戻る。
5. **未読・pending への影響**: 一時フィルタは描画時に適用される。ミュート/ブロック相手の投稿が pending に残っていても、取り込み時に除去される。バッジ・ピルの件数は Provider から届いた新着数をそのまま数える（除去は件数からは引かない。シンプルさ優先）。
6. **リロード**: 一時フィルタはセッション内のみ。リロード後はサーバー側の状態が真実で、ブロック/ミュート済みの投稿は Provider が返さない（§5.4 の検証事項に従う）。
7. **スレッドのフォーカス投稿の著者をブロック/ミュート**: ノードは unavailable プレースホルダ化。既存の取得不能ノードと同じ扱いで、会話の途切れをユーザーが理解できる。
8. **ブロック済みの相手**: 投稿がそもそも Provider 側で来ないため、メニューに「解除」を出す機会はない（解除はトースト取り消し、または本家アプリ）。
9. **quote card**: 表示専用のためメニューなし（変更なし）。
10. **自分自身への操作**: UI で項目を出さないため発生しない（万一 API が呼ばれた場合も Provider がエラーを返す）。

## 8. 将来拡張（非目標のうち、次の候補）

- **管理一覧**: ミュート・ブロック中の一覧と解除 UI（bsky: `getMutes` / `getBlocks`、misskey: `mute/list` / `blocking/list`）。設定画面の新設を伴う。
- **再共有者への操作**: `repostedBy` もメニュー項目の対象にする（`Author.id` が既に付くためモデル変更なしで追加可能）。
- **Nostr / クライアント側フィルタ**: pubkey ベースの非表示。キーワードミュートと同じ土俵で、永続化層（KV 等）とフィルタ機構をまとめて設計する。
- **Misskey のミュート期限 UI**: 本家の期限指定（無期限/1日/1週間等）に対応。
