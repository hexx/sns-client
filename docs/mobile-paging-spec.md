# スマホ UI 仕様書（スワイプページングによる複数 View 閲覧）

> 複数 SNS を1画面で扱う PWA クライアント（[sns-client-spec.md](./sns-client-spec.md)）の
> **スマホ（画面幅 <1024px）向け UI を、複数 View の横スワイプ・ページングに再定義する**拡張の確定仕様。
> 作成: grill-with-docs セッション（全8問合意）に基づく。
> 関連 ADR: [ADR-0010](./adr/0010-mobile-swipe-paging-all-mounted.md)。
> 関連仕様: [deck-view-spec.md](./deck-view-spec.md)（デスクトップのデッキ UI）。用語は [CONTEXT.md](../CONTEXT.md) 参照。

---

## 1. 背景・目的

- デスクトップのデッキ UI（[deck-view-spec.md](./deck-view-spec.md)）は複数 View を横並びカラムで常時監視できるが、スマホ（<1024px）では既存のタブ型 UI（1 View のみ表示・上部セレクタで切替）に留まり、**プロダクトの核である「複数 View の統合監視」の価値がスマホに載っていなかった**。
- 本仕様は、デッキの「横に並んだ View 群」をスマホ的に翻訳する。**View の並び順 = ページ順**の横スワイプ・ページングとし、表示していない View も裏で監視を続ける。

## 2. スコープ

### 今回（確定）
- **横スワイプ・ページング**: 全 View を左右ページとして配置。スワイプで隣接 View へ、上部タブストリップのタップで任意 View へジャンプ。
- **全ページ常時マウント**: 全 View のページを常時描画状態に保ち、ポーリング・スクロール位置・未取り込み新着を保持する（デスクトップのデッキと同等の監視性）。
- **名前付きタブストリップ（上部）**: View 名の一覧。アクティブ表示、タップジャンプ、非アクティブタブの新着バッジ。
- **ジェスチャ調停**: 横スワイプ（ページング）／縦スクロール／pull-to-refresh の軸ロック方式による両立。

### 非目標（今回は対象外）
- スマホ UI からの View 編集（追加・削除・名前変更・ソース構成編集・並び替え）。編集はデスクトップのデッキ UI に一本化する（BFF の `PUT /api/views` は共有済みのため、将来の追加は純粋なフロント作業）。
- キーボード操作・ショートカット（タブストリップのタップがタッチ非対応環境のフォールバック）。
- ページングのアニメーション詳細（減衰曲線等）の指定。

## 3. アーキテクチャ（既存踏襲）

- 単一 Cloudflare Worker（SPA 静的配信 + BFF `/api/*`、同一オリジン）の構成は不変。
- ドメインモデル不変: **View = 1つ以上の Source の集合**。各ページの実体は**既存の `TimelineCore`**（Source 群の fetch・合成・描画の本体。デッキのカラムと同一）の再利用。新規の描画機構・通知機構は導入しない。
- 更新モデル不変: 全 Source ポーリング（Misskey 15秒 / Bluesky 30秒）、新着は自動挿入せずピルで通知（[deck-view-spec.md](./deck-view-spec.md) §更新モデル と同一）。スマホでも**全 View のポーリングを常時継続**する（デスクトップのデッキが全カラムをポーリングするのと同等）。
- PWA / Service Worker 方針不変（[pwa-sw-update-fix-spec.md](./pwa-sw-update-fix-spec.md)）。

## 4. UI

### 4.1 適用条件

- 画面幅による切替は**現状維持**: `min-width: 1024px` でデッキ UI、未満で本仕様のスマホ UI（`App.tsx` の `DECK_QUERY`、deck-view-spec §7）。
- 判定は**幅のみ**。画面の向き（portrait/landscape）は判定に使わない。タブレット縦持ち（約768px）はスマホ UI、横持ち（≥1024px）はデッキ UI となる。

### 4.2 ページング

- 全 View を KV の並び順どおりに左右ページとして配置する（`GET /api/views` の配列順 = ページ順）。
- **全ページ常時マウント**: 非アクティブページも DOM 上に保持し、各 `TimelineCore` が既存ロジックのままポーリング・スクロール位置・未取り込み新着を維持する。
- ページ切替は非アクティブページのスクロール位置を保存・復元する（常時マウントのため保持は自明）。

### 4.3 タブストリップ（上部）

- 画面上部に View 名を横一列に並べる。View が画面幅を超える場合は**横スクロール**で全 View に到達可能。
- 各タブ: View 名を表示。タップでそのページへジャンプ（ページングアニメーションを伴う）。
- アクティブタブは視覚的に強調する。
- **新着バッジ**: **非アクティブタブにのみ**、その View の未取り込み新着数（ページ内ピルの件数と同一ソース）をバッジで表示。アクティブタブにはバッジを出さない（ページ内のピルがその役割を担う）。
- **バッジの消去**: その View がアクティブになったらバッジを消す。取り込み自体は既存どおりページ内ピルのタップで行う。

### 4.4 新着通知の二層構造

| 状態 | 通知手段 |
|---|---|
| アクティブページの未取り込み新着 | 既存の「N 件の新着」ピル（タップで取り込み・自動挿入しない。挙動不変） |
| 非アクティブページの未取り込み新着 | タブストリップのバッジ（件数表示） |

- スマホ固有の追加通知（トースト・システム通知等）はしない。

### 4.5 Compose

- 既存の FAB（右下フロートボタン）を維持する。全ページ共通の単一 FAB。
- Compose の挙動は [deck-compose-spec.md](./deck-compose-spec.md) / 既存モバイル Compose と同一。

## 5. ジェスチャ調停（軸ロック方式）

スマホ UI では横スワイプ（ページング）・縦スクロール・pull-to-refresh が同じ指から発生する。以下で調停する。

1. **方向ロック**: タッチ開始後、最初の移動がスロップ（**約8px**）を超えた時点で主軸を判定する。`|横移動| > |縦移動|` なら**横ロック**（ページスワイプ）、そうでなければ**縦ロック**（スクロール / pull-to-refresh）。ロックは指を離すまで変更しない。
2. **ページ切替の発火**: 横ロック後、移動量が**画面幅の約25%以上**、または**高速フリック**（速度ベース）なら隣接 View へ切替。未満ならスナップバック（現ページに戻る）。
3. **pull-to-refresh**: **縦ロック時のみ**発火可能。既存実装（`TimelineCore` の `scrollTop <= 0` 判定、タッチ専用）の挙動は不変。横ロック中は発火しない。
4. **エッジスワイプの特別扱いなし**: 画面端からのスワイプはブラウザの「戻る」ナビゲーションと衝突しうるため、開始位置による特別ルールは設けない。
5. 数値（8px / 25% / 速度閾値）は**目安**であり、実装時に操作感で調整してよい。

## 6. 操作範囲

デスクトップのデッキと同一（deck-view-spec §6）: 閲覧 + Bluesky Like / Repost、Misskey リアクション / Renote、Compose（FAB から）。返信・引用は既存モバイル UI のとおり（deck-compose-spec の非目標を踏襲）。
